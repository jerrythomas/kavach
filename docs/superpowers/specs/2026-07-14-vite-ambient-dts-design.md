# Design: `@kavach/vite` generates ambient `.d.ts` for its virtual modules

**Issue:** [#22](https://github.com/jerrythomas/kavach/issues/22)
**Date:** 2026-07-14
**Status:** Approved — ready for planning

---

## Problem

`@kavach/vite` generates the virtual modules `$kavach/auth`, `$kavach/config`,
`$kavach/routes`, and `$kavach/providers` from `kavach.config.js` at build time
(`packages/vite/src/generate.js`). It emits the **JS** but **no TypeScript
declarations** for those specifiers.

So every SvelteKit consumer hand-writes an ambient shim (e.g.
`console/src/kavach.d.ts` in `sensei-hq/sensei`) just to pass `svelte-check`.
That duplicates knowledge the plugin already has and drifts as exports change.

## Goal

`@kavach/vite` generates the ambient `.d.ts` itself and places it where the
SvelteKit toolchain already looks, so consumers delete their hand-written shim
and add nothing to their `tsconfig`.

## Non-goals

- **Literal-per-config narrowing** (e.g. `providers` typed as the exact literal
  names from `kavach.config.js`). Rejected: brittle, churns types on every
  config edit, adds generator complexity for little consumer benefit.
- Typing modules that are not emitted. The virtual-module set is fixed at four.

---

## Key decisions

1. **Write location & activation:** the plugin writes `src/kavach.d.ts`
   (path configurable) automatically at build/dev start. SvelteKit's generated
   `.svelte-kit/tsconfig.json` already includes `../src/**/*.ts`, and
   TypeScript's `*.ts` glob matches `.d.ts` files — so the generated file is
   auto-discovered by `svelte-check`/`tsc` with **zero** consumer `tsconfig`
   changes. This is the exact path the current hand-written shim occupies.

2. **Type fidelity:** reuse real `kavach` package types (`AuthAdapter`) and type
   the **full** `kavach` instance (not just `handle`). `config`/`routes`/
   `providers` get accurate **structural** types, not literal-narrowed ones.

3. **Consequence of (2):** at this fidelity the four `declare module` blocks are
   **structurally identical for every project** — they do not vary with config
   values. The value of _generating_ (rather than shipping a static file) is:
   (a) auto-placement into the path SvelteKit's tsconfig already includes, and
   (b) lockstep — the declaration text lives next to the JS generators in
   `generate.js`, so changing an emitted export changes the declaration with it.

---

## Architecture

### Component 1 — `generateDeclarations()` (pure) in `packages/vite/src/generate.js`

A pure function returning the complete ambient `.d.ts` string. No side effects,
so it is unit-tested exactly like the existing `generateModule` cases. Exported
from the package index alongside `generateModule`.

It emits a header plus four `declare module` blocks:

```ts
// Auto-generated by @kavach/vite — do not edit.
// Safe to add to .gitignore.

declare module '$kavach/auth' {
  import type { AuthAdapter } from 'kavach'
  export const kavach: {
    handle: (input: { event: any; resolve: any }) => Response | Promise<Response>
    signIn: (credentials: any) => Promise<any>
    signUp: (credentials: any) => Promise<any>
    signOut: () => Promise<any>
    onAuthChange: () => any
    configure: (options?: { invalidateAll?: () => void; logger?: unknown }) => void
    actions: (schema?: string) => any
    getCachedLogins: () => any[]
    removeCachedLogin: (email: string) => void
    clearCachedLogins: () => void
  }
  export const adapter: AuthAdapter
  export const logger: unknown
}

declare module '$kavach/config' {
  export const config: {
    adapter: string
    cachedLogins: boolean
    logging: { level: string; table?: string; collection?: string; entity?: string }
    routes: Record<string, unknown>
    endpoints: { data: boolean; rpc: boolean }
    messages: Record<string, string>
  }
}

declare module '$kavach/routes' {
  export const routes: {
    paths: Record<string, unknown>
    rules: Array<Record<string, unknown>>
  }
}

declare module '$kavach/providers' {
  export const providers: Array<{ name: string; mode?: string; label: string }>
}
```

The `kavach` instance shape mirrors the return of `createKavach` in
`packages/auth/src/kavach.js` (handle, signIn, signUp, signOut, onAuthChange,
configure, actions, getCachedLogins, removeCachedLogin, clearCachedLogins).

**What it does:** returns declaration text.
**How it's used:** called by the plugin to obtain the file contents.
**Depends on:** nothing (string builder). The consuming project must have
`kavach` installed so the `import type { AuthAdapter } from 'kavach'` resolves —
which it always does for a Kavach consumer.

### Component 2 — file-writing in `packages/vite/src/index.js`

- New plugin option **`dts?: string | false`**, default `'src/kavach.d.ts'`.
  `false` opts out entirely.
- After config parses in `buildStart`, resolve `dts` against `viteRoot`, read
  any existing file, and **write only when content differs**. This prevents
  dev-server reload loops (SvelteKit watches `src/`) and needless git churn.
- If config did not parse, skip writing (no broken-config type emission).
- Writing is best-effort: a write failure must not crash the build (log/ignore).

### Cold-`svelte-check` consideration

A CI that runs `svelte-kit sync && svelte-check` without a full `vite build` may
invoke type-checking before the plugin's `buildStart` writes the file. During
implementation, verify against `sites/demo` (which consumes `$kavach/*`) whether
`sync` triggers the write. If it does not, either (a) also write during config
resolution once config is available, or (b) document a one-line prepare step.
The chosen fix will be confirmed by an actual `svelte-check` run, not assumed.

## Data flow

```
kavach.config.js
   │  buildStart: import + parseConfig  (existing)
   ▼
parsed config ──► generateDeclarations() ──► .d.ts string
                                                │  write-if-changed
                                                ▼
                                     <root>/src/kavach.d.ts
                                                │  SvelteKit tsconfig include
                                                ▼
                                svelte-check / tsc resolves $kavach/*
```

## Error handling

- Config missing/invalid → no file written; existing behaviour (the JS `load`
  path already throws a helpful error) is unchanged.
- File write error → caught; build continues. Types are a convenience, not a
  build gate.
- `dts: false` → feature fully disabled.

## Testing

- **`spec/generate.spec.js`** — assert `generateDeclarations()` output contains
  each of the four `declare module` blocks, the `import type { AuthAdapter }
from 'kavach'`, representative full-instance members (`handle`, `signIn`,
  `actions`, `getCachedLogins`), and the auto-generated header.
- **`spec/vite.spec.js`** — `dts: false` writes nothing; default resolves to
  `src/kavach.d.ts`; unchanged content is not rewritten (write-if-changed).
  File-system interaction mocked/temp-dir'd per existing test style.
- **Integration** — write the declaration into `sites/demo/src/kavach.d.ts` and
  run `svelte-check`; expect zero errors resolving `$kavach/*` imports. This
  also settles the cold-`svelte-check` question empirically.

## Docs

- `packages/vite/README.md` — document the `dts` option and the migration:
  delete the hand-written shim, add `src/kavach.d.ts` to `.gitignore`.
- `agents/journal.md` — update on completion with commit hashes.

## Rollout / migration

For a consumer (e.g. `sensei-hq/sensei`):

1. Upgrade `@kavach/vite`.
2. Delete the hand-written `src/kavach.d.ts`.
3. Add `src/kavach.d.ts` to `.gitignore`.
4. Build or start dev once; the file regenerates. `svelte-check` passes.
